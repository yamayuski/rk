# 機能要件（F）

## F-01 署名対象

任意のバイト列を対象にする。ファイル単体、複数ファイル集合（マニフェスト）、大容量ストリームに対応。
ハッシュはコンテンツ厳密一致（バイトレベル）。可逆/不可逆変換の差異は別物として扱う。

## F-02 署名生成

デタッチド署名を標準（例: .rksig）。対象のハッシュ、サイズ、アルゴリズム、作成時刻、署名者識別子、チェーン親参照（0個=オリジナル、1..n=複製）を含む。
署名にドメイン分離文字列を含める（"rk/v1/signature" など）ことで他用途署名の混同を防止。
複数親（合成/リミックス）の場合、親署名オブジェクトのハッシュ（もしくは署名ID）参照を配列で保持。

## F-03 署名検証

対象データのハッシュ一致、署名検証、チェーン整合性（親署名の存在・検証・非循環性）の確認。
署名者鍵の有効期間/失効/ローテーション履歴の検証（AID と透明性ログの証跡を考慮）。
任意の第三者がブラウザ/CLI でオフライン検証可能（鍵・署名・対象データが揃えば検証完結）。

## F-04 署名チェーンモデル

直鎖/分岐/合流可能な有向非巡回グラフ（DAG）。
オリジナルはチェーン根（親0）。複製は1..n 親への参照を持つ。
チェーン上の各ノードにメタデータ（ライセンス/用途制限/再配布条件/言語/タグ）を任意付与。

## F-05 公開鍵の表現と配布

公開鍵のカノニカル表現と短縮フィンガープリントを規定（例: multibase + multicodec、もしくは did:key / did:web）。
「rk:key:...」形式の URI を定義し、SNS やプロフィールに掲載できる短い文字列（フィンガープリント: rkfp:...）も提供。
SNS/DNS/HTTP での所有証明フローを提供（例: DNS TXT、well-known、SNS 投稿に署名した証明文書）。

## F-06 鍵管理（複数鍵・ローテーション・失効）

作者アイデンティティはルート鍵で表現。ルート鍵が署名した AID に、アクティブな署名鍵群（Passkey/ハードウェア鍵/ソフト鍵）、有効期間、用途、アルゴリズムを列挙。
日常署名はメンバー鍵で実施。ルート鍵は稀に利用（キーローテーション/AID 更新）。
ローテーションは旧鍵→新鍵をルート鍵/リカバリ鍵で相互署名した「ローテーション宣言」で表明。透明性ログに登録。
失効は「失効宣言」（理由/時刻/対象鍵）をルート/事前登録リカバリ鍵/しきい値署名で発行。

## F-07 Passkey/ハードウェア鍵対応

複数デバイス/複数鍵を自然に扱えるよう、WebAuthn 対応を検討。ただし汎用データ署名は原理的にオリジン束縛がかかるため、
推奨: WebAuthn を「ユーザ操作承認とローカル鍵解錠」に使い、実署名はアプリ内の Ed25519 鍵で行う、または
did:key 相当の鍵を主に採用し、WebAuthn 鍵をメンバー鍵として併用（署名にクライアントデータのオリジン情報を含める設計上の注意）。
ハードウェアトークン（FIDO2/SmartCard）もメンバー鍵として登録可能。

## F-08 透明性ログ（任意→推奨）

署名オブジェクトや鍵イベント（発行/更新/失効/ローテーション）を記録する可監査な追記専用ログ（Merkle Tree）を提供。
監査証明（Inclusion Proof、Signed Tree Head）により「いつ何が公開されたか」の順序性と改ざん検知を提供。
自ホスト/連合/ミラーを想定。ログへの登録は任意だが、紛争時の証拠性を高める。

## F-09 タイムスタンプ

ローカル時刻に加え、信頼可能な時刻アンカーを任意付与（例: RFC3161、透明性ログ時刻、ブロックチェーンは任意）。
オリジナル主張の先取性証明に有用。

## F-10 ブラウザ実装/UX

ドラッグ&ドロップで署名/検証。大容量データはストリーミングハッシュ（Web Workers/Streams API）で進捗表示。
オフライン完結（Service Worker + WASM/JS 実装）。インポート/エクスポート（鍵、AID、信頼済み鍵リスト）。
エラー時の説明と再現手順の提示。アクセシビリティ（キーボード操作/スクリーンリーダ）。

## F-11 CLI/ライブラリ/API

CLI（sign/verify/keygen/rotate/revoke/aid-publish/log-submit）。
Web SDK（署名/検証/鍵操作）と WASM ビルド。サーバなしでも動作。
署名フォーマットの JSON/CBOR スキーマ、API のセマンティクスを公開。

## F-12 署名フォーマット

コンテンツハッシュ（algo, digest, size）、署名アルゴリズム、署名者（kid/公開鍵/識別子）、親参照（署名ID/署名オブジェクトハッシュ）、作成時刻、オプションのポリシー/ライセンス、透明性ログ情報、署名本体。
可能なら既存標準の活用を検討（COSE_Sign/Sign1、JWS、DSSE）。暗号アジリティ確保。
サイドカー（.rksig）を標準。将来、アーカイブ同梱（.rkpack）も検討。

## F-13 マニフェスト/複数ファイル

ディレクトリ/複数ファイルはファイルリストと各ハッシュをまとめたマニフェスト（content-addressable）に署名。
アーカイブ化によるハッシュ揺れを避けるため、マニフェストを正規化（ソート/改行/エンコーディング）。

## F-14 ポリシーと機械可読メタデータ

再配布/商用可否/AI 学習許諾などの機械可読ポリシーを署名に添付（例: SPDX ライセンス ID + ai-policy: disallow|allow with terms）。
暗号だけでは利用を強制的に阻止できないため、検知・証拠・自動フィルタ連携を想定（クローラ/データセット管理ツール向けガイドライン）。

## F-15 アイデンティティ検証の補助

SNS、Web、DNS を用いた所有証明（proof-of-possession）を半自動化するウィザード。
「rel=me」や did:web 連携、QR/リンクでの簡易認証。

## F-16 国際化/言語

署名メタデータは i18n 対応。表示はロケールに依存、署名対象は常にバイト正規化。
